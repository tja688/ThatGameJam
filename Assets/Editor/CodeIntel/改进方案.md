## 0）这个工具的“搜”的本质：Bridge 只是转发/整形，真正做语义的是 OmniSharp

README 已经把数据流讲得很清楚：外部工具打 `POST /v1/...` 到 Bridge，Bridge 再转发到 OmniSharp 的 `/goto/definition`、`/findusages`、`/findsymbols` 等接口，最后统一返回给外部工具。

所以“工具怎么搜”分两层：

* **Bridge 层**：做稳定 API、端口发现、鉴权、Unity 编译期间门控/重启、日志与容错。
* **OmniSharp 层**：对 C# 工程做语义解析与索引，提供“符号搜索 / 找引用 / 转定义”等能力。

---

## 1）你现在对外给 AI 的 3 个核心“语义动作”：输入是什么？

README 里列了 3 个 API（外加 health）：

### A) `GET /health`：探测“能不能用”

用途：Bridge 存活、OmniSharp 是否可用、Unity 是否正在编译。
这一步对 AI 很关键：**只要 Unity 正在编译/域重载，后面的语义查询很容易空/不稳定**（README 也明确提到 Unity 启动/编译阶段 OmniSharp 易短时不稳定，并做了门控与重启增强）。

### B) `POST /v1/symbols`：按“名字/关键字”找符号（Search）

请求体只有一个 `query`：

```json
{ "query": "PlayerController" }
```

它对应 OmniSharp 的 `/findsymbols`（README 的数据流说明了这一映射）。

> 这一步就是你以为的“搜 SetCurrent”：它只能给你“候选符号列表”，并不等于“找引用”。

### C) `POST /v1/definition`：给定“文件+位置”，转到定义（Go to Definition）

请求体：

```json
{ "file": "Assets/Scripts/Foo.cs", "line": 10, "col": 15 }
```

对应 OmniSharp 的 `/goto/definition`。

### D) `POST /v1/references`：给定“文件+位置”，找该位置符号的引用（Find Usages / Find References）

请求体：

```json
{ "file": "Assets/Scripts/Foo.cs", "line": 10, "col": 15, "includeDeclaration": true }
```

对应 OmniSharp 的 `/findusages`。

> 重点：`/v1/references` **不是**“按名字搜引用”，而是“对某个位置上的符号找引用”。
> 所以它是否返回“全量引用”，完全取决于：**line/col 是否真正落在你想查的符号 token 上**。

## 2）那这些操作“输出”应该是什么？（README 没写，但你可以把它固化成 AI 友好契约）

README 只定义了**请求体**，没有定义**响应结构**。
这会导致 AI 很难做稳定策略（例如：怎么从 symbols 的返回里拿到“可用于 references 的精确坐标/标识”？）。

你应该尽快把响应契约**写死**（哪怕是 Bridge 自己统一整形出来），我建议至少包含这些字段：

### `/v1/symbols` 推荐响应（最关键）

* `items[]`：

  * `qualifiedName`（全限定名，比如 `Namespace.LightVitalityModel.SetCurrent(int)`）
  * `kind`（Method/Class/Property/Field…）
  * `file`
  * `nameSpan`: `{ startLine, startCol, endLine, endCol }`（**标识符 token 的 span**，不是整段声明）
  * `declSpan`: `{ ... }`（整个声明范围，可选）
  * `symbolId`（强烈建议加：稳定 ID，后面我会说为什么）

### `/v1/references` 推荐响应

* `symbol`: 同上（让 AI 复核“我查到的到底是谁”）
* `references[]`: 每条包含 `file + span + lineText/snippet(可选)`

### `/v1/definition` 推荐响应

* `target`: `file + span + qualifiedName`

为什么我说这是“业务急需”？因为只要没有 `nameSpan/symbolId` 这类稳定锚点，AI 就会反复落到“自己去读文件算列号”的老路——你明确说这不可容忍。

## 3）为什么会出现“空引用”和“行列号问题”？——用你当前 API 设计可以严格推导出来

在你目前的接口语义下：

`/v1/references(file,line,col)` 实际做的是：

1. **先 resolve**：在这个 `file,line,col` 上解析“光标下的符号是谁”
2. **再 find usages**：对这个解析到的符号，返回引用列表

所以“空引用”一般有两大类原因：

### 类 1：根本没解析到符号（resolve 失败）→ 返回空

常见触发点：

* line/col 没落在标识符 token 上（落在空格、括号、关键字、注释等）
* 行/列基准不一致（0-based vs 1-based）
* 列的计数规则不一致（Tab/UTF/CRLF）
* 文件路径不一致（相对路径规则没写死）

这就是“行列号问题”的本质：你把“精确点中 token”的责任交给了调用方（AI），而 AI 没有 IDE 的光标语义。

### 类 2：解析到了符号，但工程状态不稳定/索引未就绪 → 结果不全或空

README 明确提到 Unity 启动/编译阶段 `.sln/.csproj` 刷新会导致 OmniSharp 短时不稳定，并且你们做了“编译期间不立即拉起 + 等工程稳定后启动”的门控增强。
这意味着：如果 AI 不先 `GET /health` 并判断 ready，就会遇到“明明应该有引用但返回空”的假阴性。

## 4）对 AI 不友好的点清单（结合你 README 现状，逐条指出）

### ① 位置型接口是“IDE友好”，不是“AI友好”

`/v1/definition`、`/v1/references` 都要求 `file+line+col`。
AI 最大痛点就是拿不到“保证落在 token 上”的 col。

### ② 端口发现/Token/随机端口：如果没有规范动作，AI 很容易踩坑

你们用 `codeintel-endpoints.json` 做端口发现，这是好事，但对 AI 来说要把它变成“固定步骤”。
另外 token 可能为空也可能非空，AI 需要稳定地从 endpoints.json 读出来并自动加 Header。

### ③ health 门控是必须的，但目前只在文档里描述，没变成“强约束协议”

既然 Unity 编译期会不稳定，应该让 AI 在调用失败时自动回到 `/health` 判断并重试（你文档已经解释了这种不稳定）。

### ④ README 没定义响应结构，导致“AI无法可靠串联 symbols → references”

这会直接诱发“工具返回了我也不知道怎么喂给下一步”的情况，最后就会被迫读文件。

## 5）针对性修改建议（按你说的“我们一起找，针对性改”——优先级从止血到升级）

### P0（立刻止血）：让 AI 不再需要读文件算 col

二选一（建议都做）：

1. **让 `/v1/symbols` 返回 `nameSpan.startLine/startCol`（标识符 token 起点）**
   AI 在第二步调用 `/v1/references` 时，直接用这个 `startLine/startCol`，命中率会高很多。

2. **让 `/v1/references` 支持 `symbolId`**（最理想）

* `/v1/symbols` 里给每个候选一个 `symbolId`
* `/v1/references` 允许 `{ "symbolId": "...", "includeDeclaration": true }`
  这样彻底摆脱行列号。

> 这两条做完，才配得上你说的“语义工具指哪打哪”，否则它只能算“IDE动作HTTP化”。

### P1（体验升级）：在 Bridge 侧做 position 容错，避免空引用

即使保留 line/col，也别直接空：

* 当 resolve 失败时，Bridge 自动在同一行附近做小范围 col 吸附（±2 或扫描最近 identifier token）
* 仍失败就返回 `candidates[]`（告诉 AI：你指到空白了，我附近识别到这些符号，你选一个）

### P1（可靠性）：把 health 变成“协议”

* `/health` 响应里明确 `isCompiling / isOmniSharpReady / lastRestartReason`
* 当不 ready 时，`/v1/*` 返回可机读错误码（例如 `CODEINTEL_NOT_READY`），AI 才能自动重试而不是瞎猜。
